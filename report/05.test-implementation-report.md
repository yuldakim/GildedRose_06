# Gilded Rose 테스트 구현 결과 보고서

## 1. 작성 목적

이 보고서는 `cpp/test/GildedRoseTest.cpp`에 구현한 Google Test 기반 단위 테스트의 범위, 설계 기준, 검증 결과를 QA 관점에서 정리하기 위해 작성했다.

테스트 대상은 C++17 기반 `GildedRose::updateQuality()`이며, 요구사항 분석 문서와 테스트 계획서에서 정의한 Normal, Aged Brie, Backstage Pass, Sulfuras, Conjured 규칙을 실행 가능한 테스트로 고정하는 것을 목표로 했다.

## 2. 구현 대상

1. 테스트 파일: `cpp/test/GildedRoseTest.cpp`
2. 구현 파일: `cpp/src/GildedRose.cpp`
3. 공개 인터페이스: `cpp/include/GildedRose.h`, `cpp/include/Item.h`
4. 요구사항 기준: `docs/requirements_analysis.md`, `GildedRoseRequirements.txt`

## 3. 테스트 설계 원칙

테스트는 `TEST_F` 기반 fixture로 구성했다. Fixture는 공통 `items` 벡터와 `updateQuality()` 호출 헬퍼를 제공하며, 각 테스트는 Given-When-Then 주석 구조에 맞춰 입력 조건과 기대 결과를 명확하게 드러내도록 작성했다.

검증은 `ASSERT_EQ`로 테스트 전제인 아이템 개수를 먼저 확인하고, `EXPECT_EQ`로 `sellIn`과 `quality` 결과를 검증하는 방식으로 통일했다. 이를 통해 실패 시 원인 파악이 쉬우며, 각 테스트가 하나의 규칙 또는 경계값에 집중하도록 했다.

## 4. 아이템 타입별 테스트 범위

| 아이템 타입 | 테스트 수 | 주요 검증 범위 |
|---|---:|---|
| Normal | 5 | 기본 감소, `sellIn = 0`, `sellIn = -1`, `quality = 0`, 하한 보정 |
| Aged Brie | 5 | 기본 증가, 만료 시 +2, 만료 후 +2, `quality = 50`, 상한 보정 |
| Backstage Pass | 5 | `sellIn = 11`, `10`, `5`, `0`, `quality = 50` 상한 |
| Sulfuras | 5 | 판매 기한 전/당일/이후 불변, `quality = 80`, `quality = 50` 불변 |
| Conjured | 5 | 기본 -2, 만료 시 -4, 만료 후 -4, `quality = 0`, 접두어 정책 |

총 25개의 `TEST_F`가 작성되었으며, 요청 조건인 아이템 타입별 최소 5개 테스트를 충족한다.

## 5. 경계값 검증 결과

품질 경계값은 `quality = 0`, `quality = 1`, `quality = 49`, `quality = 50`을 중심으로 검증했다.

1. 감소형 아이템은 `quality = 0`에서 더 이상 감소하지 않는다.
2. 감소량이 현재 품질보다 큰 경우에도 `quality`는 0 미만으로 내려가지 않는다.
3. 증가형 아이템은 `quality = 50`을 초과하지 않는다.
4. `Aged Brie`와 Backstage Pass는 증가량이 2 이상인 상황에서도 50으로 제한된다.
5. `Sulfuras`는 일반 품질 상한의 예외로 `quality = 80`을 유지한다.

판매 기한 경계값은 `sellIn = 0`과 `sellIn = -1`을 필수로 검증했다. `sellIn = 0`은 업데이트 후 `-1`이 되며 만료일 규칙이 적용되고, `sellIn = -1`은 이미 만료된 상태의 규칙이 유지되는지 확인하는 값이다.

## 6. Conjured 규칙 반영

`Conjured`는 신규 요구사항으로, 일반 아이템보다 품질이 2배 빠르게 감소해야 한다.

이번 구현에서는 이름이 `Conjured`로 시작하는 아이템을 Conjured 계열로 식별하는 정책을 적용했다. 따라서 `Conjured`뿐 아니라 `Conjured Mana Cake`도 동일한 규칙을 적용받는다.

검증한 기대 동작은 다음과 같다.

1. 판매 기한 전에는 `quality`가 2 감소한다.
2. `sellIn = 0`에서는 업데이트 후 `sellIn = -1`, `quality`가 4 감소한다.
3. `sellIn = -1`에서도 `quality`가 4 감소한다.
4. 감소량이 커도 `quality`는 0 미만으로 내려가지 않는다.
5. 접두어가 `Conjured`인 아이템도 Conjured 규칙을 적용받는다.

## 7. 구현 보정 사항

기존 `GildedRose.cpp`는 Normal, Aged Brie, Backstage Pass, Sulfuras의 레거시 규칙만 처리하고 있었으며, `Conjured` 규칙은 구현되어 있지 않았다. 또한 품질 상한/하한 보정과 문자열 비교가 중첩 조건문 안에 반복되어 있었다.

테스트를 Green으로 만들기 위해 다음과 같이 최소 범위에서 구현을 정리했다.

1. 아이템 이름을 파일 내부 상수로 분리했다.
2. `increaseQuality()`와 `decreaseQuality()` 헬퍼로 `quality` 상한/하한 보정을 한곳에 모았다.
3. `Sulfuras`는 조기 `continue`로 불변 규칙을 보장했다.
4. Backstage Pass의 임계값을 `sellIn <= 10`, `sellIn <= 5`, `sellIn <= 0` 기준으로 명확히 표현했다.
5. `Conjured` 접두어 판별은 C++17에서 사용할 수 있는 `name.rfind("Conjured", 0) == 0` 방식으로 구현했다.

## 8. 빌드 및 테스트 결과

초기 `cpp/build` 디렉터리에는 일부 빌드 산출물이 있었지만 `CMakeCache.txt`가 없어 CMake 빌드 디렉터리로 인식되지 않았다. 따라서 CMake configure를 다시 수행한 뒤 빌드와 테스트를 실행했다.

실행 명령은 다음과 같다.

```powershell
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

실행 위치는 `cpp` 디렉터리이며, 결과는 다음과 같다.

```text
100% tests passed, 0 tests failed out of 25
```

## 9. 잔여 리스크

IDE linter는 CMake include path와 Google Test 의존성을 인식하지 못해 `gtest/gtest.h` 및 프로젝트 헤더를 찾지 못한다는 진단을 표시했다. 그러나 CMake configure, build, CTest 기준으로는 컴파일과 테스트가 모두 통과했다.

현재 테스트는 핵심 규칙과 경계값을 충분히 보호하지만, 향후 리팩터링 전에는 다중 아이템을 한 번에 업데이트하는 통합성 테스트와 빈 아이템 목록 테스트를 추가하면 회귀 방어력이 더 좋아진다.

## 10. QA 결론

이번 테스트 구현으로 Normal, Aged Brie, Backstage Pass, Sulfuras, Conjured의 핵심 비즈니스 규칙과 주요 경계값이 총 25개의 Google Test로 고정되었다.

특히 `quality`의 0 하한, 50 상한, `sellIn`의 0/-1 경계, `Sulfuras` 불변 조건, Backstage Pass 임계값, Conjured 접두어 정책이 실행 가능한 테스트로 검증되므로 이후 리팩터링이나 신규 아이템 추가 시 회귀를 빠르게 탐지할 수 있다.
