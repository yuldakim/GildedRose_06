# `updateQuality()` Modern C++ 리팩토링 계획

## 1. 목표와 제약

- 대상 파일: `cpp/include/GildedRose.h`, `cpp/src/GildedRose.cpp`
- 대상 함수: `GildedRose::updateQuality()`
- 핵심 목표: 조건 분기 축소, 중복 제거, 아이템 타입/정책 분리, 매직 넘버 상수화, C++17 스타일 개선
- 필수 제약:
  - `Item` 구조체는 수정하지 않는다.
  - `Sulfuras`를 제외한 `quality`는 항상 `0..50` 범위를 유지한다.
  - 각 단계는 테스트가 Green인 상태에서만 다음 단계로 진행한다.
  - 커밋은 동작 보존 리팩토링과 동작 변경/신규 규칙 추가를 섞지 않는다.

현재 구현은 이미 범위 기반 `for`, 품질 증감 헬퍼, 일부 아이템 이름 상수, `Conjured` 접두어 판별을 포함한다. 따라서 다음 리팩토링은 대규모 재작성보다 테스트 안전망을 유지하면서 `updateQuality()`의 책임을 작은 정책 단위로 밀어내는 방향이 적절하다.

## 2. 공통 검증 명령

각 커밋 후보마다 아래 명령을 실행한다.

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

빌드 디렉터리가 없거나 CMake 설정이 갱신되어야 하면 먼저 다음 명령을 실행한다.

```bash
cmake -S cpp -B cpp/build -DCMAKE_BUILD_TYPE=Debug
```

검증 기준은 `cmake --build` 성공, `ctest` 전체 통과, Golden Master 결과 불일치 없음이다. 실패하면 해당 단계의 변경만 되돌리거나 수정하고, Green이 되기 전에는 다음 단계로 넘어가지 않는다.

## 3. 단계별 리팩토링 체크리스트

### 1단계: 테스트 안전망 확인 커밋

목표는 리팩토링 전 현재 동작을 기준선으로 고정하는 것이다.

- [ ] 기존 Google Test와 Golden Master 테스트가 모두 실행되는지 확인한다.
- [ ] `Normal`, `Aged Brie`, `Backstage Pass`, `Sulfuras`, `Conjured` 경계값 테스트가 포함되어 있는지 확인한다.
- [ ] 누락된 경계가 있으면 테스트만 추가한다.
- [ ] 제품 코드는 수정하지 않는다.

커밋 단위:

- `test: lock updateQuality behavior before refactoring`

검증 방법:

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

완료 기준:

- 모든 테스트가 Green이다.
- 실패 시 출력으로 어떤 아이템 규칙이 깨졌는지 알 수 있다.

### 2단계: 매직 넘버와 매직 문자열 정리 커밋

목표는 도메인 의미를 코드에 드러내고 후속 분리 작업의 변경 범위를 줄이는 것이다.

- [ ] `0`, `50`을 `MinQuality`, `MaxQuality`로 상수화한다.
- [ ] `2`, `3`, `5`, `10` 같은 증가량/임계값을 의미 있는 상수로 분리한다.
- [ ] 아이템 이름 상수를 `constexpr std::string_view`로 정리한다.
- [ ] `std::string`과 비교할 때는 기존 동작을 유지하는 방식으로 비교한다.
- [ ] `Conjured` 접두어 판별은 C++17 호환 방식인 `rfind(prefix, 0) == 0`을 유지한다.

권장 상수 예:

```cpp
constexpr int MinQuality = 0;
constexpr int MaxQuality = 50;
constexpr int DefaultDegrade = 1;
constexpr int ExpiredMultiplier = 2;
constexpr int BackstageFirstThreshold = 10;
constexpr int BackstageSecondThreshold = 5;
```

커밋 단위:

- `refactor: name Gilded Rose quality constants`

검증 방법:

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

완료 기준:

- 숫자와 문자열의 의미가 상수명으로 읽힌다.
- 동작 변경이 없고 Golden Master가 동일하다.

### 3단계: 품질 불변식 헬퍼 강화 커밋

목표는 `quality` 범위 보정을 한곳에서 책임지게 만드는 것이다.

- [ ] `increaseQuality()`와 `decreaseQuality()`가 `MinQuality`, `MaxQuality`를 사용하게 한다.
- [ ] 필요하면 `clampQuality()` 또는 `setQuality()`를 추가해 직접 대입을 줄인다.
- [ ] `Backstage Pass` 만료 처리의 `quality = 0`은 의미가 명확하면 `setQuality(item, MinQuality)`로 바꾼다.
- [ ] `Sulfuras`는 일반 품질 상한의 예외이므로 헬퍼 적용 대상에서 제외한다.

커밋 단위:

- `refactor: centralize quality bounds handling`

검증 방법:

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

완료 기준:

- `quality` 상한/하한 보정 로직이 중복되지 않는다.
- `Sulfuras`의 `quality = 80`이 보정되지 않는다.

### 4단계: 아이템별 함수 분해 커밋

목표는 `updateQuality()`를 순회와 디스패치 중심으로 축소하는 것이다.

- [ ] `updateAgedBrie(Item&)`를 추출한다.
- [ ] `updateBackstagePass(Item&)`를 추출한다.
- [ ] `updateNormal(Item&)` 또는 `updateDegradingItem(Item&, int baseDegrade)`를 추출한다.
- [ ] `updateConjured(Item&)`는 일반 감소 정책에 감소량만 전달하는 방식으로 중복을 줄인다.
- [ ] `decreaseSellIn(Item&)`를 추출해 `Sulfuras` 예외와 일반 아이템 흐름을 명확히 한다.
- [ ] `updateQuality()`에는 `for (auto& item : items)`와 타입 선택만 남긴다.

커밋 단위:

- `refactor: split item update rules into functions`

검증 방법:

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

완료 기준:

- `updateQuality()`의 중첩 조건이 줄어든다.
- 각 아이템 규칙이 독립 함수 이름으로 드러난다.
- 테스트 결과는 이전 단계와 동일하다.

### 5단계: Backstage Pass 규칙 테이블화 커밋

목표는 단계별 임계값/증가량을 데이터로 표현해 조건 분기를 줄이는 것이다.

- [ ] `std::array`로 `{threshold, increment}` 규칙을 선언한다.
- [ ] 판매 기한이 지난 경우는 `quality = 0`으로 먼저 처리한다.
- [ ] 그 외에는 규칙 테이블에서 첫 번째로 만족하는 증가량을 선택한다.
- [ ] 테이블 순서는 낮은 임계값부터인지 높은 임계값부터인지 명확하게 유지한다.

예상 형태:

```cpp
struct BackstageRule {
    int threshold;
    int increment;
};

constexpr std::array<BackstageRule, 2> BackstageRules{{
    {BackstageSecondThreshold, 3},
    {BackstageFirstThreshold, 2},
}};
```

커밋 단위:

- `refactor: express backstage increments as rules`

검증 방법:

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

완료 기준:

- `sellIn <= 5`, `sellIn <= 10`, 기본 `+1` 규칙이 명확히 보존된다.
- 경계값 테스트와 Golden Master가 모두 통과한다.

### 6단계: 정책 선택 함수 또는 테이블 도입 커밋

목표는 문자열 분기를 `updateQuality()` 밖으로 이동하는 것이다.

- [ ] `isSulfuras()`, `isAgedBrie()`, `isBackstagePass()`, `isConjured()` 판별 함수를 둔다.
- [ ] `updateItem(Item&)` 또는 `selectPolicy(const Item&)`를 추가한다.
- [ ] `updateQuality()`는 모든 아이템에 `updateItem(item)`만 호출하게 축소한다.
- [ ] 정책 테이블을 사용할 경우 이름 비교가 필요한 고정 아이템과 접두어 기반 `Conjured`의 우선순위를 명시한다.

커밋 단위:

- `refactor: move item dispatch behind policy selection`

검증 방법:

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

완료 기준:

- `GildedRose::updateQuality()`가 컨테이너 순회 책임만 가진다.
- 새 아이템 타입 추가 시 수정해야 할 위치가 정책 선택 영역으로 제한된다.

### 7단계: 전략 패턴 적용 여부 결정 커밋

목표는 카타 규모에 맞는 확장 구조를 선택하는 것이다. 이 단계는 반드시 필요한 구현 단계라기보다, 아이템 종류가 더 늘어날 경우의 선택지다.

전략 패턴을 선택할 조건:

- 아이템 타입이 계속 추가될 가능성이 높다.
- 타입별 규칙이 함수 몇 개로 감당하기 어려울 만큼 커진다.
- 정책 객체 단위 테스트가 필요하다.

전략 패턴 적용 체크리스트:

- [ ] `ItemUpdater` 인터페이스를 둔다.
- [ ] `NormalUpdater`, `AgedBrieUpdater`, `BackstagePassUpdater`, `SulfurasUpdater`, `ConjuredUpdater`를 분리한다.
- [ ] 팩토리 또는 정적 정책 테이블에서 아이템 이름에 맞는 업데이터를 선택한다.
- [ ] 동적 할당이 필요 없도록 정적 객체 참조 또는 함수 포인터 기반 정책을 우선 검토한다.

커밋 단위:

- `refactor: introduce item update strategies`

검증 방법:

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```

완료 기준:

- `Item` 구조체는 변경되지 않는다.
- 기존 동작과 Golden Master가 동일하다.
- 전략 도입으로 코드가 과도하게 복잡해지면 6단계의 함수/테이블 구조에서 멈춘다.

## 4. 권장 커밋 순서 요약

1. `test: lock updateQuality behavior before refactoring`
2. `refactor: name Gilded Rose quality constants`
3. `refactor: centralize quality bounds handling`
4. `refactor: split item update rules into functions`
5. `refactor: express backstage increments as rules`
6. `refactor: move item dispatch behind policy selection`
7. 선택: `refactor: introduce item update strategies`

각 커밋은 한 가지 의도만 담아야 한다. 테스트 추가 커밋과 리팩토링 커밋을 섞지 않고, 상수화와 정책 분리도 분리해서 리뷰 가능성을 높인다.

## 5. 리스크와 대응

- `Sulfuras`는 `quality = 80`이 허용되는 예외이므로 일반 `clamp` 대상에 넣지 않는다.
- `sellIn = 0`은 업데이트 전 현재 날짜로 취급된다. 조건을 `sellIn < 0`로 바꾸면 경계 동작이 달라질 수 있다.
- `Backstage Pass`는 `sellIn <= 0`에서 품질이 0이 되어야 한다. `sellIn` 감소 후 판정으로 옮기면 동작이 바뀔 수 있다.
- `Conjured`는 접두어 정책을 유지한다. `find()`를 boolean처럼 사용하면 `"Conjured"`가 맨 앞에 있을 때 오동작할 수 있다.
- 전략 패턴은 OCP에는 유리하지만 현재 규모에서는 과설계가 될 수 있다. 함수 분해와 규칙 테이블로 충분히 단순해지면 그 지점에서 멈춘다.

## 6. 최종 완료 기준

- `Item` 구조체와 공개 인터페이스를 수정하지 않았다.
- `quality` 불변식이 한곳에서 관리된다.
- `updateQuality()`는 순회와 정책 호출만 담당한다.
- 조건 분기 중복이 줄고, 아이템별 규칙이 함수 또는 정책 이름으로 읽힌다.
- 모든 단계에서 아래 검증이 통과했다.

```bash
cmake --build cpp/build --config Debug
ctest --test-dir cpp/build --build-config Debug --output-on-failure
```
