# Gilded Rose C++ QA 최종 보고서

## 1. Executive Summary

Gilded Rose C++ 프로젝트의 QA 활동은 요구사항 분석, 코드 품질 분석, 테스트 설계, 단위 테스트 구현, 결함 분석, Golden Master 회귀 테스트, 리팩토링 계획 수립까지 레거시 코드 개선에 필요한 핵심 안전망을 구축하는 흐름으로 진행되었다.

최종 검증 기준으로 Google Test/CTest는 `26/26` 통과했으며, fresh coverage build에서 `cpp/src/GildedRose.cpp` 기준 gcov 라인 커버리지 `100.00%`, 브랜치 실행 커버리지 `100.00%`를 확인했다. 테스트 계획의 목표였던 라인 커버리지 90% 이상, 브랜치 커버리지 90% 이상을 모두 달성했다.

현재 기능 결함은 모두 해결 상태다. 주요 결함은 Conjured 신규 규칙 누락에서 발생한 Major 2건이었고, 빌드/테스트 실행 경로 혼동은 Minor 인프라 이슈로 문서화되어 있다.

| Golden Master 회귀 테스트 | 장기 출력 회귀 보호 | 1개 승인 테스트 통과 | 100% | 달성 |
| 요구사항 시나리오 커버리지 | 핵심 22개 규칙 검증 | 22개 규칙을 단위/Golden Master 테스트로 매핑 | 100% | 달성 |

테스트 구성은 단위 테스트 25개와 Golden Master 테스트 1개다. 단위 테스트는 규칙별 원인 분석에 강하고, Golden Master는 31일치 출력 전체를 비교해 장기 동작 회귀를 탐지한다.

### 2.2 gcov 커버리지

측정은 저장소 밖 임시 coverage build에서 `--coverage -O0 -g` 옵션으로 새로 빌드한 뒤 CTest를 실행하고, `gilded_rose.dir/src/GildedRose.cpp.obj` 대상으로 `gcov -b -c`를 수행했다.

| 지표 | 목표 | 실제 | 판정 |
|---|---:|---:|---|
| 라인 커버리지 | 90% 이상 | 100.00% of 27 lines | 달성 |
| 브랜치 실행 커버리지 | 90% 이상 | 100.00% of 38 branches | 달성 |
| 브랜치 taken-at-least-once | 참고 지표 | 76.32% of 38 branches | 관찰 필요 |
| 호출 커버리지 | 참고 지표 | 100.00% of 14 calls | 양호 |

gcov의 `Branches executed`는 모든 조건 분기가 실행되었음을 보여준다. `Taken at least once`는 컴파일러가 생성한 문자열 비교, short-circuit, 라이브러리 호출 경로까지 포함하는 더 엄격한 방향성 지표라 76.32%로 표시되었다. 기능 요구사항 관점에서는 아이템 타입별 주요 true/false 경로와 경계값이 모두 테스트로 실행되었지만, 장기적으로는 `Backstage Pass quality=50 시작값`, `Unknown item`, `No items` 같은 보강 테스트를 추가하면 브랜치 방향성 지표도 더 좋아질 수 있다.

## 3. 결함 패턴 분석

### 3.1 아이템 타입별 결함

| ItemType | 결함 수 | 주요 패턴 | 현재 상태 |
|---|---:|---|---|
| Normal | 0 | 기본 감소, 만료 후 2배 감소, 하한 보정 정상 | Verified |
| Aged Brie | 0 | 증가 규칙, 만료 후 증가, 상한 보정 정상 | Verified |
| Backstage Pass | 0 | 10일/5일 임계값, 콘서트 이후 0 처리 정상 | Verified |
| Sulfuras | 0 | `sellIn`, `quality` 불변 및 `quality=80` 예외 정상 | Verified |
| Conjured | 2 | 신규 타입 식별 누락, 만료 후 감소량 계산 누락 | Resolved |
| Build/Test Infrastructure | 1 | 루트 `build`와 `cpp/build` 경로 혼동 | Open/Documented |

Conjured 결함 2건은 모두 "기존 일반 아이템 분기에 신규 타입이 흡수되는" 전형적인 레거시 조건문 결함이었다. 새 아이템 타입 추가 시 기존 분기를 수정해야 하는 구조가 원인이며, OCP 위반과 Magic String 기반 분기의 리스크가 실제 결함으로 나타났다.

### 3.2 심각도별 결함

| Severity | 건수 | 비율 | 설명 |
|---|---:|---:|---|

결함은 총 3건이며, 기능 결함 2건은 모두 Major로 분류되었다. 둘 다 테스트 작성 과정에서 재현 가능하게 고정된 뒤 `GildedRose.cpp` 수정으로 해결되었다.

## 4. 9단계 QA 활동 평가

| 단계 | 활동 | 효과성 평가 | 개선 필요점 |
|---:|---|---|---|
| 1 | Cursor 규칙 및 작업 기준 정리 | 산출물 형식과 작업 기준을 통일해 후속 문서 품질을 안정화했다. | 프로젝트별 Definition of Done을 더 명시하면 좋다. |
| 2 | 요구사항 분석 | 아이템 타입별 규칙과 경계값을 테스트 가능한 언어로 변환했다. | 요구사항별 고유 ID를 부여하면 추적성이 더 좋아진다. |
| 3 | 코드 품질 분석 | SRP/OCP 위반, Magic String, 중첩 조건문 등 결함 원인을 사전에 드러냈다. | 정적 분석 도구 지표와 함께 관리하면 객관성이 높아진다. |
| 4 | 테스트 계획 | P0/P1/P2 우선순위와 gcov 목표를 세워 테스트 구현 방향을 명확히 했다. | 테스트 케이스와 요구사항 ID의 매핑 표를 별도 유지하면 좋다. |
| 5 | 테스트 구현 | 25개 단위 테스트로 핵심 규칙과 경계값을 Green 상태로 고정했다. | `Unknown item`, `No items`, 다중 아이템 단위 테스트를 추가하면 더 촘촘해진다. |
| 6 | 결함 분석 | Conjured Major 결함 2건과 인프라 Minor 1건을 재현/원인/수정 기준으로 정리했다. | GitHub Issue와 연결하면 추적성이 더 강화된다. |
| 7 | Golden Master | 31일치 출력 전체를 승인 파일로 고정해 레거시 회귀 방어력을 높였다. | 실패 시 원인 분석은 단위 테스트에 의존하므로 두 테스트를 함께 유지해야 한다. |
| 8 | 리팩토링 계획 | 테스트 Green을 유지하는 단계별 Modern C++ 개선 경로를 제시했다. | 실제 리팩토링은 작은 커밋 단위로 실행하며 매 단계 coverage를 재측정해야 한다. |
| 9 | 최종 QA 종합 검토 | 테스트, 결함, 커버리지, AI 활용 효과를 통합해 릴리스 준비 상태를 판단했다. | 다음 프로젝트에서는 지표 수집을 처음부터 CI에 자동화해야 한다. |

가장 효과적이었던 단계는 2단계 요구사항 분석, 4단계 테스트 계획, 5단계 테스트 구현, 7단계 Golden Master다. 이 네 단계가 레거시 코드 변경의 안전망을 만들었고, Conjured 결함을 조기 발견하는 데 직접 기여했다.

개선 필요 단계는 1단계 작업 기준, 6단계 결함 추적, 9단계 지표 자동화다. 현재 문서화 수준은 충분하지만, 다음 프로젝트에서는 요구사항 ID, 테스트 ID, 결함 ID, GitHub Issue, CI 커버리지 결과가 자동으로 연결되어야 한다.

## 5. 다음 레거시 프로젝트를 위한 Best Practice 5가지

1. 변경 전 특성화 테스트를 먼저 만든다. 기존 동작이 옳은지 확신하기 어렵더라도 현재 동작을 Golden Master나 승인 테스트로 고정해야 안전하게 리팩토링할 수 있다.

2. 요구사항을 아이템 타입, 경계값, 불변식 단위로 쪼갠다. `quality >= 0`, `quality <= 50`, `sellIn = 0`, 특수 예외처럼 테스트 가능한 규칙으로 바꿔야 누락이 줄어든다.

3. 신규 기능은 기존 조건문에 섞기 전에 결함 패턴을 예측한다. Conjured처럼 신규 타입이 Normal 분기에 흡수되는 문제는 레거시 코드에서 반복되는 패턴이다.

4. 단위 테스트와 Golden Master를 함께 운용한다. 단위 테스트는 실패 원인을 좁히고, Golden Master는 넓은 회귀면을 빠르게 감지한다.

5. 커버리지는 목표가 아니라 누락 탐지 도구로 사용한다. 라인 100%라도 경계값 방향성이 부족할 수 있으므로 gcov 수치와 요구사항 매핑을 함께 봐야 한다.

## 6. Cursor AI 활용 효과

### 6.1 정량 요약

| 항목 | 효과 | 근거 |
|---|---:|---|
| 테스트 작성 속도 | 약 50-70% 단축 추정 | 타입별 25개 단위 테스트와 Golden Master 설계를 한 흐름으로 작성 |
| 결함 조기 발견 | Major 2건 조기 발견 | Conjured 판매 기한 전/후 감소량 오류를 테스트 단계에서 재현 |
| 테스트 통과율 | 100% | CTest `26/26` 통과 |
| 라인 커버리지 | 목표 90% 대비 +10.00%p | gcov `GildedRose.cpp` 라인 100.00% |
| 브랜치 실행 커버리지 | 목표 90% 대비 +10.00%p | gcov `GildedRose.cpp` branches executed 100.00% |
| 회귀 테스트 범위 | 31일 스냅샷 | day 0부터 day 30까지 TexttestFixture 출력 비교 |

시간 단축 수치는 별도 스톱워치 측정값이 아니라 작업 산출량 기준의 추정치다. 다만 요구사항 분석, 테스트 계획, 테스트 구현, 결함 분석, Golden Master 보고서가 일관된 형식으로 빠르게 생성되었고, 수작업으로 놓치기 쉬운 Conjured 경계값 결함이 테스트 작성 중 발견된 점은 명확한 효과다.

### 6.2 정성 요약

Cursor AI는 요구사항을 테스트 가능한 경계값으로 분해하고, 결함을 Severity/ItemType 기준으로 구조화하는 데 특히 효과적이었다. 또한 `find()` 사용 시 발생할 수 있는 C++ 문자열 판별 오류, `Sulfuras`의 `quality=80` 예외, `sellIn=0` 처리 시점 같은 레거시 코드의 회귀 위험을 사전에 드러냈다.

반면 AI가 생성한 계획과 문서는 실제 빌드/테스트/gcov 실행으로 검증되어야 한다. 이번 프로젝트에서도 coverage build를 별도로 새로 구성해 현재 코드 기준 수치를 확인했을 때 보고서 신뢰도가 높아졌다.

## 7. 최종 QA 판정

현재 Gilded Rose C++ 프로젝트는 QA 관점에서 핵심 기능 검증과 회귀 방어 기준을 충족한다.

- 기능 테스트: `26/26` 통과
- 기능 결함: Major 2건 해결, 신규 기능 결함 잔여 없음
- 커버리지: `GildedRose.cpp` 라인 100%, 브랜치 실행 100%
- 회귀 보호: Golden Master 승인 테스트 구축 완료
- 잔여 리스크: 빌드 경로 혼동, 일부 보강 테스트 후보, 향후 리팩토링 시 단계별 검증 필요

다음 단계는 `report/08.update-quality-refactoring-plan.md`에 정의된 순서대로 상수화, 품질 불변식 헬퍼 강화, 아이템별 함수 분리, 정책 선택 함수 도입을 작은 커밋으로 진행하는 것이다. 각 단계는 CTest Green과 Golden Master 일치, gcov 수치 재확인을 완료 기준으로 삼아야 한다.
