# Gilded Rose 테스트 계획 보고서

## 1. 작성 목적

이 보고서는 `docs/test_plan.md`에 작성한 테스트 계획을 QA 리드 관점에서 요약하고, 실제 테스트 구현 및 커버리지 관리 시 우선 적용해야 할 항목을 정리하기 위해 작성했다.

대상 프로젝트는 C++17, CMake, Google Test 기반이며, 테스트 대상의 핵심은 `GildedRose::updateQuality()`이다. 현재 구현은 여러 아이템 규칙이 하나의 메서드에 중첩 조건문으로 결합되어 있으므로, 리팩터링 또는 `Conjured` 기능 추가 전에 경계값 중심의 단위 테스트를 먼저 확보해야 한다.

## 2. 분석 대상

1. 요구사항 문서: `GildedRoseRequirements.txt`
2. 요구사항 분석 문서: `docs/requirements_analysis.md`
3. 테스트 계획서: `docs/test_plan.md`
4. 구현 대상: `cpp/src/GildedRose.cpp`
5. 공개 인터페이스: `cpp/include/GildedRose.h`, `cpp/include/Item.h`
6. 테스트 파일: `cpp/test/GildedRoseTest.cpp`

## 3. 테스트 전략 요약

테스트는 `TEST_F` 기반 fixture로 구성하는 것이 적절하다. 공통 fixture에서 `items` 벡터 생성, `GildedRose` 인스턴스 생성, `updateQuality()` 호출을 헬퍼로 분리하면 각 테스트가 입력값과 기대 결과에만 집중할 수 있다.

테스트명은 `ItemType_WhenCondition_ThenExpectedResult` 형식을 권장한다. 예를 들어 `NormalItem_WhenSellInIsZero_DecreasesQualityByTwo`, `Sulfuras_WhenUpdated_DoesNotChangeSellInOrQuality`처럼 이름만으로 규칙과 기대 동작이 드러나야 한다.

## 4. 우선순위별 테스트 범위

| 우선순위 | 범위 | 목적 |
|---:|---|---|
| P0 | Normal, Aged Brie, Backstage Pass, Sulfuras, Conjured 핵심 규칙 | 요구사항의 주요 동작과 회귀 위험을 즉시 보호 |
| P1 | `quality = 0, 1, 49, 50`, `sellIn = 0, -1` 경계값 | 상한, 하한, 만료 전후 조건 오류 탐지 |
| P2 | 빈 목록, 알 수 없는 이름, Conjured 접두어 정책, 다중 아이템 | 명세 해석 차이와 유지보수 리스크 완화 |

가장 먼저 작성할 P0 테스트는 다음이다.

1. Normal 아이템은 판매 기한 전 `quality -1`, `sellIn -1`이 된다.
2. Normal 아이템은 판매 기한 이후 `quality -2`가 된다.
3. `Aged Brie`는 판매 기한 전 `quality +1`, 이후 `quality +2`가 된다.
4. Backstage Pass는 `sellIn = 10`, `sellIn = 5`, `sellIn = 0` 임계값을 각각 검증한다.
5. `Sulfuras`는 `sellIn`과 `quality`가 모두 변경되지 않는다.
6. `Conjured`는 판매 기한 전 `quality -2`, 이후 `quality -4`가 된다.

## 5. 핵심 경계값

품질 경계값은 `quality = 0, 1, 49, 50`을 기준으로 잡는다.

| 값 | 검증 의도 |
|---:|---|
| 0 | 감소형 아이템이 음수로 내려가지 않는지 확인 |
| 1 | 감소량이 현재 품질보다 클 때 0으로 제한되는지 확인 |
| 49 | 증가형 아이템이 50을 초과하지 않는지 확인 |
| 50 | 증가형 아이템이 상한을 유지하는지 확인 |

판매 기한 경계값은 `sellIn = 0`과 `sellIn = -1`을 필수로 검증한다. `sellIn = 0`은 업데이트 이후 만료 상태가 되는 핵심 경계이며, `sellIn = -1`은 이미 만료된 상태에서 2배 감소 또는 증가가 유지되는지 확인하는 값이다.

Backstage Pass는 추가로 `sellIn = 11, 10, 6, 5, 1, 0`을 검증해야 한다. 이 값들은 `+1`, `+2`, `+3`, 콘서트 이후 `0`으로 이어지는 분기 오류를 가장 잘 드러낸다.

## 6. 예외 및 특이 케이스

| 케이스 | 기대 동작 | 리스크 |
|---|---|---|
| `Sulfuras` | `sellIn`, `quality` 모두 불변 | 일반 상한 50으로 잘못 보정될 수 있음 |
| `Backstage Pass` 만료 | `quality = 0` | 품질 증가 로직과 만료 후 0 처리 순서 오류 가능 |
| `Aged Brie` 상한 | 최대 50 유지 | 만료 후 +2 처리에서 51 이상이 될 수 있음 |
| `Conjured` 하한 | 감소량이 커도 0 미만 금지 | `quality = 1`에서 음수 발생 가능 |
| 알 수 없는 이름 | Normal 규칙 적용 | 문자열 분기 누락 또는 오분류 가능 |
| 빈 `items` | 예외 없이 종료 | 루프 처리 안전성 확인 |

`Conjured` 식별 정책은 테스트에서 반드시 고정해야 한다. 권장 정책은 이름이 `Conjured`로 시작하는 모든 아이템을 `Conjured` 계열로 처리하는 것이다. 이 경우 `Conjured Mana Cake`도 동일한 감소 규칙을 적용받아야 한다.

## 7. 커버리지 목표 및 측정 전략

커버리지 목표는 `GildedRose.cpp` 기준 라인 커버리지 90% 이상, 함수 커버리지 100%, 브랜치 커버리지 90% 이상이다. 요구사항 커버리지는 명세의 모든 bullet이 하나 이상의 테스트와 연결되는 것을 목표로 한다.

gcov/lcov 측정은 Debug 빌드에서 `--coverage -O0 -g` 플래그를 사용한다. 외부 의존성, 빌드 산출물, 테스트 코드는 리포트에서 제외하고 `cpp/src`와 `cpp/include`의 프로덕션 코드 중심으로 확인한다.

권장 측정 절차는 다음과 같다.

```bash
cmake -S cpp -B cpp/build-coverage -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="--coverage -O0 -g" \
  -DCMAKE_EXE_LINKER_FLAGS="--coverage"
cmake --build cpp/build-coverage
ctest --test-dir cpp/build-coverage --output-on-failure
lcov --capture --directory cpp/build-coverage --output-file coverage.info
lcov --remove coverage.info "*/_deps/*" "*/test/*" "*/build*/*" --output-file coverage.filtered.info
genhtml coverage.filtered.info --output-directory coverage-report
```

## 8. QA 결론

현재 프로젝트에서 가장 큰 테스트 리스크는 `updateQuality()` 내부 조건문이 모든 아이템 규칙을 한곳에서 처리한다는 점이다. 따라서 기능 추가나 리팩터링보다 먼저 P0 테스트로 핵심 규칙을 고정하고, P1 경계값 테스트로 `quality` 상한/하한과 `sellIn` 만료 전후 동작을 닫아야 한다.

테스트 계획의 완료 기준은 P0/P1 테스트 통과, Conjured 식별 정책 명문화, `GildedRose.cpp` 기준 90% 이상 커버리지 달성이다. 이후 리팩터링은 테스트가 보호하는 상태에서 상수화, 품질 변경 헬퍼, 아이템별 업데이트 함수 분리 순서로 진행하는 것이 안전하다.
